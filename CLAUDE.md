# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
swift build                                            # build the package
swift test                                             # run all tests
swift test --filter SankeyLayoutTests                  # run one suite
swift test --filter SankeyLayoutTests/testName         # run one test
swiftlint --strict                                     # lint (CI fails on any warning)
swift package generate-documentation --target SankeyKit  # build DocC docs
```

Demo app (`Examples/SankeyDemo`, iOS + macOS): the Xcode project is **generated by XcodeGen and must never be edited by hand** — edit `project.yml` instead, then:

```bash
cd Examples/SankeyDemo && xcodegen generate && open SankeyDemo.xcodeproj
```

## Architecture

Swift 6 package (strict concurrency), platforms iOS 17 / macOS 14 / tvOS 17 / watchOS 10 / visionOS 1. Single library target `SankeyKit` plus tests; no dependencies beyond the DocC plugin.

The rendering is a thin SwiftUI layer over a pure, view-free computation pipeline:

```
marks  →  SankeyResolution  →  SankeyGraph  →  SankeyLayoutResult  →  shapes
        (result builder)      (validation,     (scale, stacking,     (Path,
                               layering)        Bézier geometry)      hit testing)
```

- `Content/` — the mark types (`SankeyLink`, `SankeyNode`), `SankeyContentBuilder` (result builder mirroring `ViewBuilder`: `if`, `if`/`else`, `for` work), and per-mark modifiers. Nodes are implicit: naming one in a link creates it; a `SankeyNode` mark only customizes an existing node.
- `Model/` — `SankeyResolution` (flat list of resolved links + node overrides from walking the content tree), `SankeyGraph` (drops self-links and non-positive values, merges duplicate endpoints, rejects cycles with a readable path instead of crashing), `SankeySelection`, `SankeyValue` (labelled values, mirrors `PlottableValue`; labels feed VoiceOver).
- `Layout/` — `LayerAssignment` (longest-path layering, as in d3-sankey), `SankeyLayout` (plain `CGRect`s and Bézier control points, no view types — this is why geometry is unit-testable directly), `RibbonGeometry`, `AnimatableVector`.
- `View/` — `SankeyChart` (public entry), `SankeyDiagram`, one SwiftUI shape per element (`NodeShape`, `RibbonShape`) rather than a `Canvas`, so hit testing, per-element accessibility and shape interpolation come for free. Chart modifiers (`.sankeyNodeWidth` etc.) are environment-backed via `SankeyConfiguration`/`SankeyStyle`, composable like `chartXAxis`.

Fill resolution has three levels, most specific first: style set on the mark → color scale (`.sankeyColorScale`) → built-in palette.

Errors: problems are logged to the `de.peterkurzok.SankeyKit` subsystem; a graph that cannot be laid out draws a readable diagnostic instead of an empty view.

## Conventions

- Never commit directly to `main`: branch first, then open a PR with `gh pr create`. CI (SwiftLint strict + build & test on macOS) must pass before merging.
- Prefer testing behavior through the pure layers (`SankeyGraph`, `SankeyLayout`) rather than through views; the layout engine is covered by the tests in `Tests/SankeyKitTests`.
- SwiftLint is strict in CI with many opt-in rules (`.swiftlint.yml`); run it before committing.
- Implementation plans live in `docs/agents/plans/` (dated markdown files).
