# Contributing to SankeyKit

Thanks for taking an interest. Bug reports, questions and pull requests are all welcome.

## Workflow

Never commit to `main` directly. Branch from it, then open a pull request:

```bash
git switch -c my-change
# …work…
gh pr create
```

CI must be green before a pull request is merged. It runs SwiftLint, builds and tests the package,
and compiles it for every platform in `Package.swift`.

## Before you push

```bash
swift build
swift test
swiftlint --strict          # CI fails on any warning
```

`swiftlint --strict` is the one that catches people out: `.swiftlint.yml` enables a long list of
opt-in rules, and CI treats every warning as an error.

## Tests

The rendering is a thin SwiftUI layer over a pure, view-free pipeline:

```
marks  →  SankeyResolution  →  SankeyGraph  →  SankeyLayoutResult  →  shapes
```

Prefer testing behavior through `SankeyGraph` and `SankeyLayout` rather than through views — they
are plain value types, so geometry and validation can be asserted directly. Tests live in
`Tests/SankeyKitTests` and use Swift Testing.

## Documentation

Public API carries DocC comments; the catalog is `Sources/SankeyKit/Documentation.docc`. Build it
with:

```bash
swift package generate-documentation --target SankeyKit
```

## The sample app

`Examples/SankeyDemo` is generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen). **Never
hand-edit `SankeyDemo.xcodeproj`** — it is not committed. Edit `Examples/SankeyDemo/project.yml`
instead, then regenerate:

```bash
cd Examples/SankeyDemo
xcodegen generate
open SankeyDemo.xcodeproj
```

## Changes worth discussing first

For anything larger than a bug fix, open an issue before writing code — it is cheaper to agree on
the shape of an API before it exists than after.
